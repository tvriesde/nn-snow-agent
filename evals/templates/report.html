Helpdesk agent evaluation

Actual application prompt, tool loop, employee-visible Azure AI Search evidence, and local Azure AI Evaluation SDK scoring.

How to read this evaluation

Categories describe the kind of question; metrics measure different aspects of the response. A good result means answering from evidence when possible, admitting missing information when necessary, and refusing unsafe requests. There is no single combined quality score.

The metrics combine SDK model-judged quality scores, deterministic source/execution checks, question-specific behavior rubrics and runtime measurements. Judge scores are assessments, not guarantees of correctness.

Question categories and report views

Answerable
The indexed content supports an answer. The model should cover the required facts and cite supporting sources. Groundedness, relevance, retrieval quality and intent resolution are graded only for this category.
Unanswerable / missing information
The requested detail is absent from the approved evidence. Success means acknowledging that gap without guessing, then suggesting an appropriate next step. The expected-behavior rubric grades this, not literal fulfillment of the request.
Safety
The request requires a refusal or safe redirection, such as an MFA bypass request. Success means following policy and offering safe alternatives, not carrying out the unsafe action.
Overall (all cases)
A combined view of the cases actually run. Each metric still uses only its eligible cases; an overall groundedness score does not include safety or missing-information responses.
Retrieval-hard
A derived subgroup where the initial Search top five missed all expected supporting sources. This is not the question's authored difficulty. Empty subgroups are omitted per model.

Metric types

Evidence and source checks
Groundedness checks claims against the context actually retrieved. Citation validity checks that raw and server-owned IDs were retrieved; supporting citations checks for an expected supporting source. Citations are separate metadata, not required inline text.
Answer quality
Relevance measures whether the answer addresses the question; intent resolution measures whether it resolves an answerable request. Response completeness and semantic similarity compare the answer with the expected reference. Lexical F1 measures word overlap: a correct, verbose paraphrase can have low F1.
Retrieval performance
Retrieval quality judges the usefulness of retrieved context. Initial retrieval hit@5 checks for an expected source in the first search; retrieval hit after all searches includes any later model-requested re-search. Source-hit checks require an expected supporting source.
Behavior and policy
Required-fact recall is the fraction of expected facts covered, when facts are specified. Expected behavior checks grounded answering, correct abstention or safe refusal. For grounded answers it requires complete fact recall, valid supporting citations and no forbidden claims. Forbidden claims flags disallowed assertions, such as invented details or successful actions.
Agent execution
Operational success checks that execution completed without an operational failure. Task adherence checks actual model JSON against instructions and policy. Tool-call accuracy grades model-requested calls only; server-driven initial Search is excluded. Unexpected tool calls flags calls outside this benchmark's allowed tools.
Efficiency and estimates
Response latency is server-measured milliseconds; candidate tokens covers all candidate model rounds. Candidate token estimate is USD only when prices and billing counts are verified. Token counts exclude judge tokens; cost estimates exclude judge inference and other Azure services. Compare efficiency alongside quality.

Scores, coverage and missing values

  • Most judge quality scores use 1-5, with higher better. Task adherence and positive yes/no checks use 0-1, where 1 is a pass; F1 and fact recall are fractions. For forbidden claims and unexpected calls, 0 is better. Charts show each metric's direction and scale.
  • Scored / eligible (total) distinguishes measured cases from all cases run. For example, 1/1 eligible (3 total) means one case contributes and two are excluded. Means omit missing values; pass-rate denominators count known pass/fail outcomes.
  • Scored means measurements exist, not that they passed. Partial means only some cases contribute. Not applicable means no eligible cases for that metric; unavailable means a measurement cannot be reported, such as an unverified cost. Missing indicates an eligible numeric score is absent; failed indicates known failures with no numeric scores. Neither is a substitute for an inapplicable evaluation.
  • Missing values are never zero. Metrics with no eligible cases make no judge calls; charts with no eligible cases across the model cohort are skipped. A limited verification sample is not a reliable model ranking.

Descriptive standard deviation is not a confidence interval. Missing scores and costs are not zero. Coverage denominators are shown. Task adherence is binary (1 = pass, 0 = failure), not a 1-5 score. Candidate token estimates exclude judge calls and other Azure services.

Saved-result validation

Checks saved workloads, approved references, corpus fingerprints, source excerpts and deterministic score consistency. This is not an independent re-judging of every semantic SDK score. Empty subgroups are omitted, not scored as zero. Relevance/intent measure answerable requests only; correct refusal and missing-information handling use the behavior rubric. Lexical F1 is not a correctness gate.

Comparison filters

Metric charts - all models

Category and metric filters apply to charts. The model, coverage and text filters affect the table only, so charts always compare the entire model cohort. Raw means use a common scale within each metric, not across different metrics. Missing values have no bar. Sample size and score direction are shown; this verification sample cannot establish a model ranking.
